# Codex lifecycle compatibility

The only active route is Codex + `opencode-go-bridge` + OpenCode Go + `deepseek-v4-flash`.

## Managed files and state

- Codex config: `$CODEX_HOME/config.toml`
- Catalog: `$CODEX_HOME/models-with-deepseek.json`
- Role: `$CODEX_HOME/agents/DeepSeek.toml`
- State: `%LOCALAPPDATA%\deepseek-subagent\` on Windows (manifest, backups, bridge runtime metadata, legacy roster archive), with `DEEPSEEK_SUBAGENT_STATE_HOME` available for isolated tests.
- Diagnostic Agent roster: `<installed-skill-root>\.local\agents.json` (since 1.6.8, sharing one lifecycle with `.local\handoffs`); schema v3 stores only Agent id, its verified native parent thread id/evidence, stable role, scope, nickname, deterministic project handoff path/key, lifecycle state, and timestamps. Normal reads are restricted to the current root task. Every roster read is ownership/diagnostic evidence only; it never proves process-local operability or exposes a recovery action. Schema v1/v2 entries remain readable and report `legacy_unconfigured` until a project handoff is explicitly bound.

Schema v4 retains internal `platform="codex"` and `provider="opencode-go"` fields so existing transactions and backups remain readable. Older schemas and legacy state locations are read safely. Historical selection fields do not appear in normal status and do not choose a route; the next successful setup or repair writes a converged manifest.

## Ownership and rollback

The manager owns only its marked Provider block, `model_catalog_json`, `features.multi_agent`, `features.multi_agent_v2`, the managed catalog entry, and `DeepSeek.toml`. It records installed and previous values and restores fields with compare-and-swap semantics. Unrelated TOML content and comments are preserved.

`disable` is transactional and idempotent. `uninstall` first verifies the active or disabled hashes, runs a healthy disable, restores owned fields, then removes the managed manifest. Drift or a field conflict stops finalization and preserves recovery data.

For a partial uninstall, resolve the reported field conflict, then run:

```text
repair --json
disable --json
uninstall --json
```

Backups, old markers, old schema payloads, and the legacy state directory remain readable solely for safe rollback. They are not product choices.

## Protocol boundary

`cross-provider-v1`, Responses/SSE conversion, DSML promotion, reasoning replay, full-history replay, previous-response continuation, call_id correlation, deduplication, and SessionStore TTL/capacity/locking remain unchanged. v1.4.0 relocates the stable localhost token to the installed Skill's `.local` directory; migration preserves its generation and fingerprint, and restart still never rotates it. v1.4.1 raises the managed DeepSeek role's default reasoning effort from `high` to the highest supported level, `ultra`. v1.4.2 adds parent-side lifecycle guidance that prefers `send_input` and `resume_agent`. v1.4.3 makes every child persistent by default and reserves close or replacement for explicit user decisions.

v1.5.0 introduced a durable, non-secret Agent roster and an experimental original-id recovery policy. It also normalized Codex-persisted `reasoning.content` to the empty array required by the OpenCode Go replay schema while preserving only supported reasoning metadata; validated and repaired the exact ONLOGON task command, including native UTF-16 `schtasks /XML` output; recorded the next-login workdir separately while an older bridge was still running; and adopted the new bridge PID written after a Windows reboot. The bridge improvements remain supported. The child-recovery policy was later disproved and is superseded by v1.6.0.

v1.5.1 makes Multi-Agent V1 the only legal DeepSeek cross-provider transport. Setup and repair keep `features.multi_agent_v2=false` and the configured parent/DeepSeek catalog entries on `v1`; the runtime gate also reads the current task's persisted rollout `turn_context` and verifies the actual parent model entry before any spawn, resume, or subsequent send. V2 or unconfirmed evidence fails closed with no V2 fallback. A current task already initialized as V2 cannot be repaired in place. The bridge explicitly rejects V2-only `agent_message + encrypted_content` and does not decrypt it.


v1.5.2 moves safe repair ahead of the first child request. `prepare --json` is the default mutating preflight: it checks the installed Skill version, managed static configuration, bridge/autostart state, and current task evidence; repairs only Skill-owned drift; reloads the bridge when an in-place Skill upgrade would otherwise leave old code resident in memory; and then applies the same fail-closed V1 transport gate. The non-mutating `transport check` remains available for diagnosis. When the current task is already V2, `prepare` cannot change it in place, but it also adds that task's actual parent model to the managed V1 catalog for the next task before returning `configured_new_task_required`. Missing user-owned credentials remain a hard stop and are never synthesized or copied.

v1.5.3 hardens both recovery boundaries. Bridge health is no longer identity evidence: a managed process is identified by its PID, process creation time, exact script/interpreter, workdir, and fixed token paths, with an exact Task Scheduler command fallback for legacy instances. Missing manager metadata can be rebuilt from strong bridge artifacts; an unhealthy verified bridge can be restarted before the first child operation; an unverified process is preserved and never killed. Task Scheduler queries use bounded timeouts.

The stable localhost token also fails closed. Fingerprint/state drift is repaired without changing the token body or generation. Existing empty/unreadable token files and orphan metadata never trigger implicit rotation. Temporary files receive the restricted ACL before atomic replacement, so ACL failure preserves the previous secret.

Roster schema v2 binds every new child to the authoritative parent id in its native Codex rollout. Normal `agents list` output is current-parent-only; `--all-parents` is diagnostic, and cross-parent entries expose no recovery action. Legacy entries without parent fields remain non-operable unless their own rollout resolves them without ambiguity. Roster state never proves liveness. Only a fresh child reply proves `live`, and only a concrete prior-assignment fact in that fresh reply proves `context preserved`.

After a complete Codex exit, Windows restart, `shutdown`, or `not_found`, the old DeepSeek child is outside the supported operability boundary. Its durable rollout and roster entry remain useful for audit and handoff, but the Skill does not call `resume_agent`, does not expose `recovery_action`, and does not infer liveness from persistence. An unrelated root task must never adopt the old root's children.

v1.5.4 keeps the installed release tree immutable while the managed bridge is running. Task Scheduler launches `pythonw` with `-B`, and the standalone entry point also disables bytecode before importing the runtime package. Normal start, restart, and ONLOGON recovery therefore do not repopulate `__pycache__` or `*.pyc`. The strict legacy identity parser accepts the prior no-`-B` command only when its executable, script, workdir, port, PID artifacts, and process start evidence all match.

v1.5.5 fixes resumed full-history tool-result replay. Codex-persisted `function_call_output` and `custom_tool_call_output` items may contain private `content` and control fields that are not legal in the upstream Responses input schema. The upstream boundary now emits only canonical `type`, `call_id`, and `output`, requires the authoritative `output` field, and never guesses tool results from private content. This removes the `ArrayParam input[i].content array_above_max_length` failure without exposing or rewriting the durable child transcript.

v1.5.6 completes strict resumed-history normalization. Persisted assistant output messages are converted from Responses `content:[output_text]` to the chat-style assistant context accepted by OpenCode Go, while the adjacent visible reasoning text is replayed through `reasoning_content`. Native function calls are also reduced to canonical `type`, `call_id`, `name`, and `arguments`. Private Codex fields are never forwarded, prior answer text remains available for context recovery, and unknown content shapes fail locally instead of being guessed or sent upstream.

v1.5.7 adds fail-closed cross-provider recovery identity auditing. Native Codex evidence showed that a Store/Desktop build can reattach the original child thread id while subsequent `send_input` turns use the parent model instead of `deepseek-v4-flash`; those turns never reach the managed bridge. Upstream Codex V1 source confirms that `resume_agent` constructs the reopened child config from the live parent turn and passes no persisted agent role. Main-session provider-bucket migration, such as rewriting `session_meta.model_provider` and `threads.model_provider`, can preserve history visibility but cannot restore that V1 in-memory child role; this Skill therefore never edits durable conversation/index state as a routing workaround. The roster compares the original and latest child `turn_context` model/Provider/V1 identity and exposes `resumed_agent_model_provider_drift`. Desktop model override rejection and the absence of a separately installed CLI are platform boundaries, not reasons to install software or rewrite durable state.

v1.6.0 finalizes the reduced product scope. DeepSeek delegation is supported only inside the current Codex process and current verified root while the native registry still recognizes the child id. The roster is retained for ownership isolation, diagnostics, explicit retirement, and successor handoff, but `operable_by_current_parent=false`, `recovery_action=null`, and `cross_restart_recovery_supported=false` are intentional. Historical identity drift is a doctor warning rather than a bridge failure, so it cannot block an explicitly requested new child. `prepare` and the transport gate expose `safe_to_spawn_send`; the old resume-oriented capability field is removed.

The same release adds explicit successor continuity without claiming runtime recovery. `agents handoff-init` creates or reuses a deterministic project-local Markdown log keyed by stable role and scope; `handoff-start` issues a non-secret per-turn token plus a byte-length/SHA-256 baseline; `handoff-check` accepts only when the entire prior byte prefix is unchanged and the exact token marker appears in newly appended bytes. Roster schema v3 binds each child to that log and enforces one global `open` owner per actual handoff path across all roots. Ordinary cross-root registration fails with `handoff_owned_by_other_parent`; the explicit, user-authorized `successor-register` action atomically changes the old lease to `superseded`, installs the new sole owner, and increments `handoff_generation` without claiming native closure or recovery. Every child turn must read the log first and append a compact context/result/evidence/open-risk record before replying. A post-restart child with the same stable role, scope, and project root reads and continues the file even when its generated nickname differs. This preserves explicit project knowledge, not the old Agent process, hidden context, or chain-of-thought. Strong PID identity, V1-only routing, credential safety, strict fresh-reply semantics, and all protocol normalization fixes remain supported.

v1.6.1 fixes the first `prepare` after a complete Codex restart without reviving the unsupported child-runtime recovery goal. Bridge compatibility is now governed by an explicit bridge ABI rather than the Skill release version. A healthy identity-verified ABI-compatible process is reused across Skill patch updates. Normal bridge launch is detached and on demand; ONLOGON is no longer a readiness gate. ## Runtime behavior and diagnosis

Operational details for diagnosis; normal Codex operation follows SKILL.md.

### prepare

`prepare` is idempotent and safe to re-run. It repairs only Skill-owned Codex configuration, the managed catalog/role, and the on-demand bridge runtime before the first child request of a task. A healthy identity-verified bridge is reused whenever its bridge ABI is compatible; a Skill patch-version change alone does not restart it. When a restart is genuinely required, a compatible bridge first receives an authenticated, instance-bound self-shutdown request (`/control/shutdown`). If a verified legacy process cannot be stopped (control ABI absent and Windows denies termination), `prepare` preserves its evidence, starts one isolated replacement on a dynamic localhost port, and repairs the managed Provider to that port exactly once; if replacement also fails it returns `bridge_process_unrecoverable` with the old PID and earliest evidence instead of looping. `prepare` never terminates a Python process whose bridge identity is unverified. It then reads `CODEX_THREAD_ID`, finds that task's rollout, verifies the latest `turn_context.multi_agent_version` is `v1`, and confirms the actual parent model's selected catalog entry is also `v1`; missing, ambiguous, or V2 evidence fails closed with no V2 fallback. A current task already initialized as V2 cannot be changed in place: `prepare` adds that task's actual parent model to the managed V1 catalog for the next task and returns `configured_new_task_required`. `transport check` is the non-mutating diagnostic form of the gate.

### Bridge lifecycle

The managed bridge is on-demand and listens only on `127.0.0.1`. Process identity uses the PID, process creation time, exact script/interpreter, workdir, and fixed token paths, with an exact Task Scheduler command fallback for legacy instances; health is never identity evidence. ONLOGON autostart is not created by the normal lifecycle, and a legacy managed autostart task is removed when a healthy compatible bridge is reused. Missing manager metadata (`bridge-runtime.json`) can be rebuilt from strong bridge artifacts; an unhealthy verified bridge can be restarted before the first child operation; an unverified process is preserved.

### Token and ACL

The localhost token is fixed at `<skill-dir>\.local\local-bridge-token.txt`; bridge and Codex `auth.command` read the same file. A normal restart preserves its body, generation, and fingerprint. Since 1.6.6 an existing, readable, fully consistent token takes a fast path that never rewrites the ACL: `ensure_token` uses it directly, so a normal `prepare` never requests elevation merely to re-harden an already-good ACL. ACL repair happens only on fresh token creation, explicit rotate/restore/legacy migration, metadata mismatch (repaired around the same token body), or a failed read: an Access Denied read repairs the ACL once, re-reads once, and then fails closed without looping or rotating. On Windows, ACL repair grants only the current execution SID and the real profile SID resolved from the Windows `ProfileList`; a sandbox `whoami` is never the sole principal, incomplete resolution preserves the existing ACL and fails closed, and ACL repair never reads, rewrites, rotates, fingerprints, or prints the token. An empty/unreadable token or a missing body with existing metadata fails closed instead of implicit rotation. Only `bridge rotate-token` rotates it. Distinguish `local_bridge_token_acl_repair_failed`, `local_bridge_token_invalid`, `local_bridge_token_unreadable`, and `local_bridge_token_missing` from `upstream_key_invalid`; never collapse them into a generic `Invalid API key` message.
