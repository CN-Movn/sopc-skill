# Windows development and verification

Use the installed PowerShell launcher. It discovers Codex Python without changing `PATH` or copying the runtime. Since 1.6.15 the Windows default state root (manifest, backups, operation lock) is `<installed-skill-root>\.local\state`; the old `%LOCALAPPDATA%\deepseek-subagent` root is only a read-only legacy discovery source (`_legacy_appdata_root`) for pre-1.6.14 manifest/roster/bridge metadata and is never written by the normal path. Use `DEEPSEEK_SUBAGENT_STATE_HOME` or `--state-home` for isolated tests.

```powershell
$skill = "$env:USERPROFILE\.codex\skills\deepseek-subagent"
powershell -NoProfile -ExecutionPolicy Bypass -File "$skill\scripts\deepseek-subagent.ps1" credentials status --json
powershell -NoProfile -ExecutionPolicy Bypass -File "$skill\scripts\deepseek-subagent.ps1" status --json
powershell -NoProfile -ExecutionPolicy Bypass -File "$skill\scripts\deepseek-subagent.ps1" doctor --e2e --json
powershell -NoProfile -ExecutionPolicy Bypass -File "$skill\scripts\deepseek-subagent.ps1" bridge status --json
powershell -NoProfile -ExecutionPolicy Bypass -File "$skill\scripts\deepseek-subagent.ps1" prepare --json
powershell -NoProfile -ExecutionPolicy Bypass -File "$skill\scripts\deepseek-subagent.ps1" transport check --json
powershell -NoProfile -ExecutionPolicy Bypass -File "$skill\scripts\deepseek-subagent.ps1" agents list --json
powershell -NoProfile -ExecutionPolicy Bypass -File "$skill\scripts\deepseek-subagent.ps1" agents list --all-parents --json
```

Create `%USERPROFILE%\.codex\skills\deepseek-subagent\.local\opencode-go.key` manually and place the OpenCode Go Key on exactly one line. The runtime never searches another credential source and never writes this file. Setup, repair, update, and managed-file synchronization must preserve it.

## Cross-computer installation

Copy only a clean source/release tree to another computer. Never migrate the active installed directory and never package its `.local` directory: a live `pythonw` bridge can hold installed files open, while `.local` intentionally contains machine-bound ACL principals, bridge PID/runtime paths, the manually provisioned Key, roster ownership, handoffs, and absolute project roots. On the target computer, place the clean controlled tree at `%USERPROFILE%\.codex\skills\deepseek-subagent`, create the target computer's `.local\opencode-go.key` manually, start Codex, run `prepare` once in a new task, and continue only when the V1 gate is ready.

A Codex task is also bound to its workspace path. Moving or deleting that workspace while the task is open, or opening the task on a computer where that absolute project path does not exist, is a task/workspace migration failure rather than a Skill runtime dependency. Keep the workspace in place until the task is finished, or open a new task against the target computer's existing project directory. Copying a clean release tree does not require stopping the source computer's bridge; use `reinstall-prep` only when intentionally removing an installed tree.

The stable localhost token is `%USERPROFILE%\.codex\skills\deepseek-subagent\.local\local-bridge-token.txt`. Bridge and Codex `auth.command` use that same file. The token ACL principal set is stable across identities: `.local\local-bridge-acl-principals.json` (secret-free) records the profile owner SID and every observed sandbox SID; once recorded, a sandbox SID is kept by all later hardening/repair even when the current identity is the elevated profile owner, so elevated `icacls` rewrites never delete the sandbox ACE. Historical Administrator-only ACLs are bootstrapped once: the sandbox first persists the stable principal evidence (fail-closed with `local_bridge_acl_principal_state_write_failed` on write failure, `local_bridge_acl_principal_state_invalid` on corrupt/unsupported state — never guessed, never widened), the existing controlled elevation then repairs with the full stable set, leaving token body, generation, and fingerprint untouched; afterwards the fast path applies (readable token, zero ACL repairs). An existing readable, consistent token is used directly (fast path, no ACL rewrite); Access Denied repairs the ACL once, re-reads once, then fails closed. On Windows, ACL repair grants only the profile owner SID plus recorded sandbox SIDs; a sandbox `whoami` is never the sole principal, incomplete resolution preserves the existing ACL and fails closed, and ACL repair never reads, rewrites, rotates, fingerprints, or prints the token. Metadata mismatch is repaired using the existing token body. An empty/unreadable file or missing body with existing metadata returns a stable local-token error and requires explicit operator action; it is never treated as first install.

The canonical diagnostic Agent roster is `<installed-skill-root>\.local\agents.json`, sharing one lifecycle with `.local\handoffs`: restarts and upgrades preserve both, and deleting the whole installation removes both. Roster mutations (`register`, `successor-register`, `retire`) serialize on `<installed-skill-root>\.local\locks\agents.lock` (same `.local` domain; AppData `deepseek-subagent.lock` is not used), with slow native child/parent verification performed before the lock and the authoritative `agents.json` read-modify-write inside it; lock timeouts return structured `operation_in_progress`. A legacy `%LOCALAPPDATA%\deepseek-subagent\agents.json` is consumed exactly once: it is copied to the canonical file and then archived by rename to `agents.json.migrated-v1.6.8.bak` (history kept, never read again, never re-imported by a later clean reinstall). A legacy file still matching the canonical content is archived silently; a divergent legacy file is archived out of the discovery path as `agents.json.legacy-conflict-<hash>.bak` and reported as `roster_legacy_conflict_archived` (canonical kept, no merge, nothing overwritten). Archive failures fail closed with `roster_migration_finalize_failed` and roll back the half-migrated canonical file. Use `DEEPSEEK_SUBAGENT_STATE_HOME` for isolated state-root tests. Schema v3 registration stores no prompt, source, tool output, Key, or bridge token. Each new entry is bound to the parent id verified from native Codex rollout evidence and to a deterministic machine-local handoff log under the installed Skill's `.local\handoffs`. Normal listing is current-parent-only; `--all-parents` is diagnostic. Entries carry ownership facts only (id, role, scope, nickname, parent evidence, handoff binding and status, state, generation, timestamps, successor references, `parent_match`, `owned_by_current_parent`); constant policy fields (`operational_scope`, `cross_restart_child_recovery_supported=false`, `roster_purpose`, liveness/context policy) appear once at the payload top level. Roster evidence alone never proves operability, liveness, or context preservation, and entries expose no recovery action.

`setup`, `repair`, and `prepare` use an on-demand detached `pythonw` bridge. Since 1.6.14 all normal bridge mutable state lives under the installed Skill's `<installed-skill-root>\.local\bridge`: `bridge-runtime.json`, the `runtime\` workdir (`bridge.json`/`bridge.pid`), and replacement/recovery directories; normal `prepare` performs zero writes to `%LOCALAPPDATA%\deepseek-subagent`. The legacy AppData state root is accepted read-only (`legacy_state_root`): an old AppData bridge is discovered without writing, then safely stopped via the authenticated shutdown and restarted into the canonical root; legacy files that cannot be cleaned are preserved. They do not require or create an ONLOGON task during the normal lifecycle, and remove a legacy managed autostart task when reusing a healthy compatible bridge. Bridge identity uses process creation time and exact managed artifacts independently of `/health`; this permits recovery of an unhealthy bridge while preventing termination of an unrelated Python process. The health response and `bridge.json` publish a separate integer bridge ABI. A Skill version change alone does not restart a healthy bridge when that ABI is compatible.

Since 1.7.1, first-use token writes and bridge launch are independently serialized. Before a fixed-port launch mutates `bridge.pid` or `bridge.json`, lifecycle management checks the actual IPv4 loopback listener PID. If a failed contender overwrote `bridge.pid` while `bridge.json` and the Windows process identity still prove which managed process owns the listener, status repairs the PID evidence and recovery safely targets only that verified process. Otherwise it returns `port_busy` or `bridge_listener_pid_mismatch` and preserves all unverified processes. Local `/health` and control calls use a no-proxy opener, and a rejected local bearer token is reported as `local_bridge_token_invalid`.

The managed `pythonw` command includes `-B`, and `bridge_standalone.py` sets `sys.dont_write_bytecode` before importing the runtime package. A bridge start or restart must therefore leave the installed managed tree free of `__pycache__` and `*.pyc`; clean old cache during upgrade without touching `.local`.

`prepare` is the first-operation-per-task preflight: run it once per Codex task/root before the first DeepSeek operation and again only after a concrete bridge/transport/config failure; healthy later `send_input` turns skip it. It idempotently repairs safe Skill-owned drift in Codex configuration, the managed catalog/role, and bridge runtime. A healthy identity-verified bridge is reused when its ABI is compatible. When restart is genuinely required, the current ABI supports a localhost bearer-authenticated shutdown bound to the exact bridge instance id. If a verified legacy process cannot be stopped because its control ABI is absent and Windows denies process termination, `prepare` keeps the old evidence, starts one isolated replacement on a dynamic localhost port, and repairs the Provider to that port once. If replacement also fails, return `bridge_process_unrecoverable` with the old PID and earliest evidence; do not loop or require routine elevation. `prepare` then reads `CODEX_THREAD_ID`, finds that task's rollout, verifies its latest `turn_context.multi_agent_version` is `v1`, and confirms the actual parent model's selected catalog entry is also `v1`. Missing, ambiguous, or V2 evidence fails closed and never falls back. If the current task is V2, `prepare` may prepare that actual parent model for the next task but reports `configured_new_task_required` rather than claiming the current task changed in place. `transport check` remains the non-mutating diagnostic form of the V1 gate.

`status` and `doctor --e2e` validate the V1 transport gate, static configuration, persistent Agent roster readability, Key-file presence, running bridge process, compatible bridge ABI, on-demand launch mode, `auth.command`, localhost token authentication, and a minimal `/responses` inference. Only the complete chain returns `configured`; failures include the earliest stage and a stable error code. A missing legacy ONLOGON task is not a failure.

For repository tests, call the selected interpreter explicitly and force UTF-8:

```powershell
$env:PYTHONDONTWRITEBYTECODE = '1'
$env:PYTHONUTF8 = '1'
& $python -m unittest discover -s .\deepseek-subagent\tests -v
```

The runtime has one package tree at `deepseek-subagent/runtime/deepseek_subagent`. Codex lifecycle code lives in `platforms/codex`; OpenCode Go bridge code lives in `bridges/opencode_go`.

Pass an explicit temporary `handoff_root` in tests so logs never touch the real Skill `.local`; the production default is `<installed-skill-root>\.local\handoffs`. Verify deterministic same-role/same-scope naming inside that store, automatic creation of a missing store, multi-project isolation when identical role and scope are used with different project roots, absence of `<project-root>\.deepseek-subagent`, legacy project-local detection with `legacy_handoff_migrated=false`, incompatible-path failure, exact appended turn-token checks with an unchanged SHA-256 prefix, adversarial full-history rewrite rejection, legacy schema migration, same-root active-owner conflict, cross-root `handoff_owned_by_other_parent`, and explicit successor transfer to one new `open` generation while the old owner becomes `superseded`. Also cover canonical-roster resolution with one-time migration from a legacy AppData roster (ownership, generation, and successor references preserved, legacy file kept), conflicting canonical/legacy content failing safe without overwrite, the `handoff-init` ownership preflight blocking a foreign `open` owner before any spawn while allowing the current parent's own owner and ignoring `superseded`/`retired` entries, and `reinstall-prep` returning `ready_for_reinstall=true` after a verified authenticated bridge stop (idempotent with no bridge, fail-closed on unverified identity or failed stop). For a Windows-reboot bridge test, seed an old runtime PID plus a fresh matching `bridge.pid`/`bridge.json`, then verify `BridgeLifecycle.status()` adopts the fresh PID and reports the bridge running. Also cover missing runtime metadata, missing `bridge.json`, an unhealthy-but-identified process, an unverified PID that must be preserved, a repaired task whose future workdir differs from the current bridge, and stop/restart/rotate-token after PID adoption. Bridge reboot recovery enables future new children only; it does not recover a pre-restart child. The successor continues only the explicit project Markdown handoff.
